## §2 · The method, which is the point

Both sides call **`step_cell_at` from `src/fold/field_leaf.h`**. Not two implementations that agree — that is a claim about two authors' care, and it decays the first time one of them is edited — but **one function compiled twice**, which is a claim about C++ and about integers.

§12 keeps `osv_core.cuh`'s leaves for exactly this reason, and states it better than I can: *"every function the field advances by is `OSV_HD`, so `g++ -x c++` and `nvcc` emit the same arithmetic. Not 'the same equations' as a promise — the same translation unit as a property."*

So R2.1's first work was not writing kernels, it was **factoring R1.1's arithmetic out of the host class** into a header that allocates nothing, holds no container, and touches no float. The host `Field::step_cell` is now one line over that leaf; the kernel is one line over the same leaf. The 50 field oracles from R1.1 pass unchanged after the refactor, which is how I know the extraction did not change what it moved **[M]**.

`-fmad=false` is passed deliberately and is **inert**: there is no floating-point multiply for the compiler to contract. QC-1 and QC-2 measured 22 percent divergence between contraction settings on the float version of this code; pinning a flag that can no longer matter is how you demonstrate that it no longer matters **[D]**.

## §3 · The projection, under 20,000 concurrent atomics

`k_project` runs one thread per cell, accumulating with `int64` atomics in whatever order the scheduler chooses. It matches the host's ordered loop **exactly**, including for negative amounts — the fixture deliberately carries them, because two's-complement `atomicAdd` on `unsigned long long` is how a signed sum is done on the device and it is worth proving rather than assuming **[M: `gpu.proj.bit_identical`]**.

This is the property integer accumulation buys, and it is worth restating in the terms `osv_core.cuh` used: *"a float `atomicAdd` is order-dependent, so the same ledger would project to a bit-different lattice on two runs and every replay claim in the system would be false."*

## §4 · The sweep, and why order cannot matter

Red-black Gauss-Seidel: one block per segment, one thread per cell, two colour passes. No cell reads a same-colour neighbour, so within a pass every read is of a value nothing is writing — which is what makes the device version a **port of the host loop rather than a second algorithm**. 40 iterations, 1,536 lattice cells, and the two agree on every one, flags included **[M]**.

The harness carries its own lie arm: perturbing one device cell by **one unit** must be visible. It is **[M: `gpu.sweep.lie.one_unit_of_difference_is_visible`]**. A bit-identity harness that cannot see a single unit of difference is measuring nothing, and that check costs four lines.

## §5 · The delta this rung earns

**§5's tier table should move the sweep from *bounded* to *exact and portable*.** The blueprint's row reads:

> | bounded | agreement to a stated envelope with no verb flips … | the sweep, every judge margin, every shadow tape across tuples |

The sweep no longer belongs in that row. Measured across two compilers, two architectures and two execution orders, it is bit-identical, which is the *exact and portable* row's claim — the same row that already holds "integer folds only: state, field projection, caps, kappa counts". **The field's relaxation now qualifies for it too**, and the reason is R1.1's constraint that relaxation coefficients be dyadic rationals over a power-of-two denominator.

Stated with its limits, because a receipt that overclaims is the defect it warns about: this is **two** tuples, not all tuples. A different card generation, a different nvcc, or an ARM host are unmeasured. What is now established is that the *class* of divergence QC-1 and QC-2 measured — float contraction differing between builds — cannot occur here, because there is no float. Judge margins and shadow tapes remain in the bounded tier and are untouched by this.

## §6 · What R2 still owes

The blueprint's R2 row also asks for **the embedding store and exhaustive scan**, gated on "scan timed at the embedder's real dimension". That is a separate component and is not built.

Neither is a **throughput** number for the kernels, deliberately: the lattice in this harness is 1,536 cells, which is the right size to test arithmetic and the wrong size to time a card. A sweep timing belongs with a realistic lattice, and that comes with the embedding store.

The peer process itself — §4.3's socketless reader of committed deltas over a named pipe, applying in batches at commit boundaries and publishing `applied_pos` — is also R2 work and is not built. What exists after this rung is the arithmetic, proven identical on both sides of the bus; what does not exist is the process that would run it there.
