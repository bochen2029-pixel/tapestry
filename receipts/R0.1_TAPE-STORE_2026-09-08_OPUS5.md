**[M]** Three readings, one conclusion:

## §6 · The defect this rung found, and the law it broke

The oracles were green (88/88) before the kill harness ran. **100 hard process kills under load found a real defect that no synthetic test had reached.**

**Symptom [M].** `killA/t20`, after a kill and a reopen:
```
seg-00000000000000002637.jsonl:1: POSITION BREAK have 2637 want 2628
CHAIN BROKEN
```
The last complete row on the tape was position 2627. The reopened tape resumed at **2637** — a permanent nine-position gap in the deposit clock.

**Cause [D].** A segment file is named by its first position, and a roll opens that file while the batch that will fill it is still pending. A kill in that window leaves a file whose *name* is a position that was assigned but **never published**. Recovery then read the name as a position. §4.1 is explicit — *positions and hashes are published only after the flush returns* — and naming a file for an unpublished position publishes it through the file system. The blueprint's own `sz == 0` recovery clause ("open loads `prev` from the previous segment's last row or the header") is what encoded the mistake: it says the header may be trusted, and after a roll it cannot be.

**Fix [SPEC].** A trailing segment holding **no complete row** — empty, or nothing but the torn remains of one — carries no entry, is the ghost of an uncommitted roll, and is discarded at open; the head comes from the last complete row, which is the only authority. Both shapes are now regression oracles (`ghost.*`), and the discard is a `warn` entry on the tape (`uncommitted_segment_discarded`), because a store whose recovery is silent cannot be audited. The fatal rule is unchanged where it belongs: a segment with bytes, no complete row, **and no earlier segment to continue from** is fatal, never genesis.

**Frequency [M].** Not a corner: **12 of 100 kills** landed in that window.

**Kill runs, after the fix — 200 hard kills across two arms [M]:**
```
> powershell -File build/killtest.ps1 -Iterations 100                          (flush per batch)
kills=100  killed_mid_row=0  killed_between_rows=100  uncommitted_roll=12
reopened=100  verified_rows_total=178717  FAILURES=0
KILL TEST OK

> powershell -File build/killtest.ps1 -Iterations 100 -NoSync -Batch 512        (widened write window)
kills=100  killed_mid_row=0  killed_between_rows=100  uncommitted_roll=75
reopened=100  verified_rows_total=1695353  FAILURES=0
KILL TEST OK
```
Every reopen recovered, every recovered tape verified with zero breaks, every discard left its named `warn` row, and no `warn` row appeared without the condition that earns it. 1.87 million rows verified after 200 kills.

`killed_mid_row=0` in **both** arms is itself a finding **[D]**. With a flush per batch the writer spends nearly all of its wall time inside `FlushFileBuffers`, so a kill almost never lands inside `WriteFile`; the second arm removed the flush and widened each write to ~200 KB (512 entries) to hunt for the torn row, and still did not hit one in 100 kills — a `WriteFile` of that size returns faster than the kill's own scheduling window. The torn-row path is real (a power loss or a media error can tear at any offset) but on this box it is reachable only synthetically, which is exactly what the `torn.*` oracle does. Recording it here so a later rung does not mistake "we never saw one" for "it cannot happen".

## §7 · Deltas against the blueprint, for the next QC

Four, each small and each load-bearing. Nothing here contradicts a measurement; they are places where building the thing found the text underdetermined.

1. **Two kinds are added to §3.1's table: `seg` and `warn`.** `seg` is the segment header *as a chained entry* — the first row of every segment, body `{"first_pos":N,"prev_of_first_entry":"<64hex>"}`. §4.2 requires a header carrying both fields but does not say where it lives; making it an entry rather than a sidecar means the chain crosses a roll with **zero seams** (the estate's verifier confirms it in §4 above), the header cannot be lost separately from its segment, and it is self-checking, since its body's `prev_of_first_entry` must equal its own `prev`. It costs one position per roll. `warn` is already used in §4.1 and §4.2's prose and is simply missing from the table.
2. **The ghost rule** of §6 above, which §4.2's recovery clause needs and does not have.
3. **Non-UTF-8 carriage has a spelling**: `{"$b64":"…"}`, one member, that tag. §3.1 says "base64 with a type tag" without naming it.
4. **Floats.** §3.1's v0 form has no float rule; the writer emits `%.17g` and can be told to refuse floats entirely with the typed reason `float_forbidden`, which is what fold-facing paths use. The FACTOR joint amendment (`qc/NEXT_FROM-FACTOR_2026-09-08.md` item 2) wants canonical JSON with **no floats and declared-width integers as strings**; that is a wire change and is deliberately **not** taken here, because it would break the byte-level compatibility §4 just demonstrated. It belongs to the v1 binary form, and this receipt is the argument that v0 should stay as it is until then.

## §8 · What R0.1 does not do

R0's full scope (§9) also carries: the idempotency cache keyed on `(client_id, request_id)`; typed refusals in two classes, entries and counters; the constraint language as scalar UDFs in DuckDB with threads pinned to one and float aggregates forbidden inside folds; the client socket with length-prefixed frames; and the fault injector. None of those are in this rung. The remaining R0 gates are therefore still open:

- *the refusal that never silences* — needs the transactor's refusal path;
- *1,000 kills lose no acknowledged entry and keep no unacknowledged one* — the tape half holds (§6); the acknowledgement half needs the reply cache. **Note for that rung:** under a *process* kill the OS retains written-but-unflushed bytes, so a batch written and not yet flushed can survive as unacknowledged entries. The gate is satisfiable as stated only for power loss; for process kills the honest form is *no acknowledged entry is lost, and an unacknowledged one that survives is deduplicated by the reply cache on retry*. This is flagged now rather than discovered at the gate.
- *a redelivered suffix does not double-count*, *a retried write applies once* — both need the reply cache.

DuckDB is not installed on this box (`python -c "import duckdb"` → `ModuleNotFoundError` **[M]**) and no download was made; the constraint evaluator's dependency is an open decision for R0.2.
